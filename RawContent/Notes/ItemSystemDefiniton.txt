**Full Description of the Intended Item System**  
*(Updated 2026-08-12 – current locked design + next priorities)*

### 1. High-Level Goals
- Fully data-driven item definitions using Primary Data Assets + Fragments.
- One `UItemInstance` = one physical item in the world (no stacking of instances).
- World representation is always an `AItemActor` that is never destroyed on pickup.
- Clean separation of concerns:
  - **Data** → Definitions + Fragments
  - **Runtime state** → `UItemInstance`
  - **World presence** → `AItemActor`
  - **Player holding logic** → `UHeldItemsComponent`
  - **Presentation** → Animation, Control Rig, Physics Control (mostly Blueprint + component)

### 2. Core Code Types

**UItemDefinition** (Primary Data Asset)  
Contains an array (or map) of `UItemFragment*` instances.  
This is the pure data definition of an item type (Stick, Axe, Unarmed, etc.).

**UItemFragment** (abstract base)  
Lightweight, instanced, edit-inline objects that add specific capabilities.  
Examples: Stackable, Durability, Fuel, Equippable, Damage.

**UItemInstance**  
Runtime object that points to its `UItemDefinition` and holds any per-instance state (current durability, etc.).  
Created by the factory. Never stacked.

**AItemActor**  
The actual actor in the world.  
- Owns a static mesh component.  
- Holds a reference to its `UItemInstance`.  
- Implements `IItemActorInterface`.  
- Can be simulated or driven by Physics Control.  
- Survives pickup/drop cycles (never destroyed on pickup).

**UItemFactory**  
Responsible for spawning `AItemActor` + creating the matching `UItemInstance`.  
Always spawns single-item instances.

**EHand** (in `WoodcraftTypes.h`)  
```cpp
UENUM(BlueprintType)
enum class EHand : uint8
{
	Left,
	Right,
	None
};
```

### 3. Equippable System

**UEquippableFragment** (minimal)
```cpp
bool bTwoHanded = false;
```

**Hand Ownership**
- One primary hand owns the item (`EHand::Left` or `EHand::Right`).
- When `bTwoHanded == true`, the opposite hand is treated as secondary.
- Player can hold two different one-handed items at the same time.

### 4. Animation & Attachment Architecture (Locked)

Two skeletal meshes on the player:

- **FPArmsMeshAnimRef** (invisible, no collision, truth source for pose info)  
  Pure animation authority. Plays all montages and hold poses. Performs **zero** IK.  
  Physics Control is attached to `WeaponBone_L` / `WeaponBone_R` on this mesh.

- **FPArmsMeshVisible** (visible, IK to held item)  
  Copies the pose from AnimRef every frame, then applies Control Rig IK to the grip targets supplied by `UHeldItemsComponent`.

**Physics Control** (not classic Physics Constraint)  
- One `UPhysicsControlComponent` named PhysicsControl on the character.
- When an item is held, a control is created that drives the item relative to the corresponding WeaponBone on the AnimRef.  
- Gives the item real momentum and physical reaction while still following the hand.  
- Strength will later be tuned (and possibly driven by item mass) for light vs heavy feel.

**Dynamic Grip Transform**  
Every frame the component calculates:

```
Relative = AnimRef.HandBone.GetRelativeTransform(AnimRef.WeaponBone)
GripTarget = Relative * ItemWorldTransform
```

This keeps the visible hand locked to the actual physics-driven item while automatically staying correct for any animation.  
Left-hand IK works correctly with this method without extra mathematical mirroring of the transform.

**Left-hand item mesh mirroring**  
For simplicity and to avoid future inconsistencies with asymmetrical items, the held item mesh will be mirrored (scale X = -1) when held in the left hand.

### 5. UHeldItemsComponent Responsibilities

- Manages both hands (`HeldItemLeft` / `HeldItemRight`).
- Always has a valid item in each hand (Unarmed item when empty).
- `TryPickup` / `TryDrop`.
- Creates / destroys Physics Controls on attach / detach, immediately replacing one item with another (picked up -> unarmed, or vice versa)
- Dynamically calculates grip transforms every frame for Control Rig IK.
- Mirrors the item mesh when held in the left hand.
- Notifies the item actor when it becomes held or released.
- Provides clean Blueprint API.

### 6. Player Structure

- C++ class `AWoodcraftCharacter` owns the `UHeldItemsComponent`.
- WoodcraftPlayer Blueprint is a subclass of AWoodcraftCharacter.
- C++ owns state and rules; Blueprint owns presentation (animation, Control Rig, Physics Control tuning, meshes).

### 7. Unarmed Handling (Locked)

Unarmed is a **real item** (`DA_Unarmed` + simple mesh).  
Both hands start with Unarmed on BeginPlay.  
Dropping an item immediately equips Unarmed in that hand.  
This eliminates null-hand special cases throughout the pipeline.

### 8. Current Status (as of 2026-08-12)

**Working**
- Item Factory + spawning
- `AWoodcraftCharacter` + `UHeldItemsComponent`
- Physics Control attach to AnimRef WeaponBones
- Dynamic grip transform calculation (right and left hand IK targets correct)
- Basic hold feel with Physics Control

**Known remaining polish on hold**
- Disable collision on the held item when the Physics Control is stretched too far or the item goes behind the player (caught on geometry)
- Always mirror left-hand held item mesh
- Strength vs item mass tuning of physics control (later)

### 9. Next Priority Order

1. **Held item safety**
   - Disable collision (and possibly lower Physics Control strength) when the item is stretched too far from the WeaponBone or ends up behind the player.

2. **Left-hand item mesh mirroring**
   - Scale X = -1 on the item mesh when held in the left hand (simple, permanent solution for the current item set).

3. **Full Pickup / Drop loop**
   - Q held = pickup/drop mode
   - Camera trace for looked-at item
   - LMB = left hand, RMB = right hand (spatial default, with future settings flip)
   - Pickup montage on AnimRef + Anim Notify to finalize Physics Control attach
   - Drop breaks control, restores simulation, equips Unarmed

4. **Item Highlight**
   - All equippable items within pickup radius → subtle gray stencil / custom depth
   - Currently looked-at item → stronger pale green / yellow
   - Reuse existing stencil material

5. **Basic Extend functionality**
   - Soft references to neutral vs extended animation assets
   - Ability to swap them on the fly (for reaching / interacting)

6. Later: swinging, inventory, two-handed, damage application, etc.
