**Harvestable System Definition**
*(Updated 2026-08-16 – crops/farming direction locked; fragment naming convention updated 2026-08-19)*

### 1. High-Level Goals

- Provide a data-driven system for large world resources that the player damages or processes over time (trees, ore veins, clay deposits, large rocks, stumps, etc.).
- Keep clear separation from the Item system: Harvestables exist primarily to be interacted with in the world and eventually *produce* Items.
- Mirror the successful patterns already locked for Items and Creatures (Definition → Instance → Actor + Fragments) for consistency.
- Support multi-stage destruction and transformation (standing tree → fallen log Item + stump, ore vein → ore chunks, etc.).
- Remain efficient for high-density placement during dynamic world generation.
- Support crops / farming as a first-class extension of the same architecture.

### 2. Core Architecture

**UHarvestableDefinition** (Primary Data Asset)
- Pure type data for a harvestable resource.
- Contains an array of `UHarvestableFragment*` (EditInlineNew, Instanced).
- Examples: DA_OakTree, DA_PineTree, DA_CopperVein, DA_ClayDeposit, DA_Stump_Generic, DA_Carrot, DA_BerryBush, etc.

**UHarvestableFragment** (abstract base)
- Lightweight, primarily pure data (EditDefaultsOnly).
- Two virtuals mirroring the Item system:

```cpp
/** Called once when a UHarvestableInstance is first created. */
virtual void OnInstanceCreated(UHarvestableInstance* Instance) {}

/** Called every time an AHarvestableActor is spawned/initialized. */
virtual void OnHarvestableSpawned(AHarvestableActor* Actor) {}
```

**UHarvestableInstance** (UObject, outer = TransientPackage or owned by subsystem)
- Long-lived runtime state for a specific harvestable (current health, stage, quality, regrowth timer, growth progress, water, etc.).
- Created **lazily** for world-generated resources (see section 4).
- Player-planted crops always create an Instance immediately.
- Destroyed only when the resource is fully harvested / removed.

**AHarvestableActor** (single base class, like AItemActor and ACreatureActor)
- The world representation.
- Holds a reference to its Definition (always) and to its Instance (when one exists).
- Handles collision, visual representation, damage reception, stage transitions, and growth visuals.
- May be destroyed and later recreated from an Instance if needed (streaming, save/load).

**UHarvestableFactorySubsystem** (UWorldSubsystem) – or methods living on a broader Environment/Resource subsystem
Public API sketch:
```cpp
UHarvestableInstance* CreateInstanceFromDefinition(UHarvestableDefinition* Definition);
AHarvestableActor*    SpawnActorFromDefinition(UHarvestableDefinition* Definition, const FTransform& Transform);
AHarvestableActor*    SpawnActorFromInstance(UHarvestableInstance* Instance, const FTransform& Transform);
void                  PromoteToInstance(AHarvestableActor* Actor); // creates Instance on first meaningful interaction
```

### 3. Relationship to the Item System

Harvestables are **not** Items.

- When a harvestable is fully (or partially) processed it **produces** one or more Items by calling into `UItemFactorySubsystem`.
- Example transitions:
  - Standing tree trunk dies → spawn DA_Log Item(s) + spawn Stump Harvestable.
  - Log (now an Item) is further chopped → spawn Wood Chunk Items.
  - Ore vein depleted → spawn Ore Chunk Items.
  - Stump destroyed → spawn 2–3 Wood Chunk / Wood Scrap Items.
  - Mature crop harvested → spawn produce / seed / cutting Items.

This keeps the Item system as the single authority for anything that can be picked up, held, stored, or used in crafting.

All real Items continue to simulate physics by default. Harvestables may use more complex collision / falling behaviour while they are still Harvestables.

### 4. Lazy Instance Creation (Important Optimization)

Most trees and simple deposits placed by world generation have no unique state at spawn time.

Rule:
- World generation (or foliage systems) may spawn a pure `AHarvestableActor` that only stores a soft/hard reference to its `UHarvestableDefinition`.
- No `UHarvestableInstance` is created yet.
- On the first meaningful interaction (first damage that changes state, or any event that needs persistence), the Actor calls `PromoteToInstance()`.
- From that point the Instance owns the runtime data and the Actor simply references it.

This keeps memory and UObject count low for dense forests while still giving full Instance power the moment it is needed (partially chopped trees, quality variation, save games, etc.).

Player-planted crops always start with an Instance because they carry unique growth state from the moment they are placed.

### 5. Damage & Interaction

Both `AItemActor` and `AHarvestableActor` should implement a shared interface (name TBD – `IDamageable`, `IHarvestable`, or similar).

The interface provides a common entry point for tools:

```cpp
UINTERFACE()
class UDamageable : public UInterface
{
	GENERATED_BODY()
};

class IDamageable
{
	GENERATED_BODY()
public:
	virtual void ApplyDamage(const FDamageInfo& DamageInfo) = 0;
	// FDamageInfo would carry amount, damage type / tags, instigator, hit location, tool, etc.
};
```

Tool impact logic then works uniformly against anything that implements the interface. Exact shape of `FDamageInfo` and damage calculation is still open (see Open Questions).

### 6. Example: Tree Lifecycle

**Standing Tree** (`AHarvestableActor` + Tree Definition)
- Full collision that pushes the player and other Items.
- Fragments can include: Fallable, Branchable, YieldTable, Health, ToolRequirement (axe tags), etc.
- Branch hits can spawn Stick / Branch Items and remove visual parts without killing the whole tree.
- When trunk health reaches zero:
  1. Play fall sequence (physics or animation + physics).
  2. Destroy / hide the standing tree Actor.
  3. Spawn one or more `DA_Log` Items via ItemFactory.
  4. Spawn an `AStumpActor` (simple Harvestable).

**Fallen Log**
- Now a normal Item (`UItemInstance` + `AItemActor`).
- Further processing (removing remaining branches, chopping into wood chunks) happens entirely inside the Item system.
- Matches the vision note: “Logs must have branches removed before they can be picked up (two hands) or used.”

**Stump**
- Lightweight Harvestable.
- On destruction spawns 2–3 Wood Chunk / Wood Scrap Items and removes itself.

### 7. Crops & Farming (Locked Direction – 2026-08-16)

Crops are a first-class use of the Harvestable system.

#### 7.1 Core Rules

- A growing plant is an `AHarvestableActor` + `UHarvestableInstance` for as long as it exists in the world.
- On harvest it produces normal Items via `UItemFactorySubsystem` (produce, seeds, cuttings, fiber, etc.).
- Wild plants use the normal lazy-Instance path.
- Player-planted plants always create the Instance immediately (they have unique growth state from day zero).
- Multi-harvest plants (berry bushes, etc.) stay as Harvestables after picking and can regrow fruit.
- Single-harvest / root crops are destroyed (or left as a spent root/stump) after harvest.

#### 7.2 Seeds & Cuttings (Items)

**Seeds**
- Normal stackable Items, Size S.
- Visual: small pile mesh.
- Fully compatible with containers (put in / take out like any other resource).
- Some seeds will later be edible / cookable (e.g. sunflower seeds).
- Planting consumes one “use” from the pile (or one item if pure stacking is preferred later). When uses reach zero the Item is destroyed.
- Other future uses (seed oil, crafting, etc.) remain open.

**Cuttings**
- Larger Items (Size SM or M depending on species).
- Custom mesh per crop type.
- Planting a cutting skips the earliest stages and starts the plant at **Sprout** or early **Growing** with a larger starting scale and higher initial health.

#### 7.3 Planting (MVP)

- Direct planting on the ground is supported.
- No tilling or terrain modification for the first version.
- Each crop authors a `MinPlantDistance` (cm). On plant attempt a simple overlap check rejects placement if another crop is too close.
  - Dense small crops (carrot, radish-type): ~12–18 cm
  - Medium: ~20–30 cm
  - Larger / bushy: ~40–70 cm
- Alignment / hex or rectangle snap can be added later and can reuse the structure blueprint placement system.
- Planter boxes / raised beds will be Structures (preferred). They will provide strong soil quality, protection, and density bonuses later.
- Planting flow (high level): hold seed/cutting → look at valid ground → activation → short placement → consume use/Item → spawn young `AHarvestableActor` already owning an Instance.

#### 7.4 Growth Stages

Default ordered stages (per-crop overrides allowed):

1. **Sprout** – tiny visible plant, appears immediately on successful plant
2. **Seedling**
3. **Growing** (vegetative)
4. **Flowering** (optional)
5. **Fruiting** and/or **Seeding**

- No fully invisible germinating phase. A tiny sprout appears right away for clear player feedback.
- During Sprout and early Growing, relative scale (and optionally material parameters) is driven by progress inside the stage for smooth visual growth.
- Hard mesh swaps occur at major stage boundaries when geometry needs to change.
- Early-stage meshes (tiny sprout / seedling) can be shared across many crop species.
- Fruiting vs Seeding is crop-specific:
  - Some plants have a clear Fruiting stage (high produce, low seed) that later transitions into a Seeding stage (produce drops, seed yield rises).
  - Others combine them into one mature stage whose yield table shifts with further progress or season.

#### 7.5 Growth Model

Stage-based with continuous progress inside each stage.

Each stage has a base `DurationInGameDays`. Progress advances as:

```
Progress += (DeltaDays / StageDuration) * SeasonMult * SoilMult * WaterMult * HealthMult;
```

When Progress ≥ 1.0 the plant advances stage, resets Progress, and updates mesh / collision / yields.

**Timing anchor**
- Real-world carrot ~60–80 days → in-game target **~15–20 days** under normal conditions (≈ 6–8 real hours at 24-min days).
- Perfect conditions can reduce total time by roughly ¼–⅓.
- Poor conditions slow growth significantly or halt it (multipliers approach zero).

Soil quality for MVP is sampled once from the biome / microbiome at plant location and stored on the Instance. No ongoing voxel soil simulation.

Water level and consumption exist as future extension points; they are not required for the first playable crops.

Different crops simply author different stage durations and different sensitivity to the multipliers.

#### 7.6 Harvest & Yield

- Yield tables live per stage (or on a dedicated yield fragment).
- Harvest interaction (hand or tool) when the current stage allows it:
  - Spawns the appropriate Items via ItemFactory.
  - Either destroys the plant, leaves a spent root/stump, or resets it to a post-harvest stage (multi-harvest).
- Taking cuttings is a separate or modified interaction on suitable stages of certain species.
- Destructive dig for root crops yields the tubers (+ possible replantable pieces) and removes the plant.

#### 7.7 Still Open / Future

- Exact planting input binding and montage.
- Precise default stage durations and multiplier curves (will be tuned once a test crop exists).
- Watering mechanics and tools.
- Fertilizer / soil improvement beyond the initial biome sample.
- Visual authoring budget and shared early-stage meshes.
- How aggressively seasons gate certain crops.

### 8. Fragments – Initial Ideas

These are starting points only; exact set will evolve.  
**Naming convention (locked 2026-08-19):** concrete fragments use `<Capability>HarvestableFragment`.

- `UHealthHarvestableFragment` – MaxHealth, current health lives on Instance.
- `UYieldHarvestableFragment` – what Items to spawn and in what quantities / chances when destroyed or on stage change.
- `UFallableHarvestableFragment` – fall behaviour, direction bias, physics settings for the falling phase.
- `UBranchableHarvestableFragment` / `UPartDamageHarvestableFragment` – support for damaging individual parts (branches) independently.
- `UToolRequirementHarvestableFragment` – gameplay tags or damage types this harvestable responds to.
- `UMultiStageHarvestableFragment` – ordered list of stages with different meshes / health / yields (used by both trees and crops).
- `URegrowHarvestableFragment` – for stumps or plants that can return over time.
- Crop-oriented:
  - `UGrowthHarvestableFragment` – stage list, base durations, MinPlantDistance, starting stage for seeds vs cuttings.
  - `USeasonalHarvestableFragment` – preferred seasons / temperature / humidity windows + multipliers.
  - `USoilPreferenceHarvestableFragment` – preferred biome tags and soil quality response.
  - `UWaterHarvestableFragment` – consumption rate, drought thresholds (future).
  - `UPropagationHarvestableFragment` – which stages allow seeds or cuttings and the resulting Item definitions.
  - `UMultiHarvestHarvestableFragment` – for plants that can be picked repeatedly.
  - `UCropHarvestableFragment` – convenience / collision + growth related settings for crops.

### 9. World Generation & Performance Notes

- Dense static resources (trees, small rocks) should prefer Hierarchical Instanced Static Meshes or Foliage where possible.
- Interaction can be handled by a lightweight manager that, on hit, either:
  - Spawns a full `AHarvestableActor` at that location and transfers state, or
  - Directly applies damage logic and spawns Items without a persistent Actor for trivial cases.
- Only resources that need ongoing unique state (partially damaged, high-value veins, player-planted crops) become full Actors + Instances.

Exact streaming / density strategy is still open.

### 10. Open Questions / Needs Further Discussion

1. Exact name and shape of the shared damage interface (`IDamageable` vs `IHarvestable` vs something else) and the `FDamageInfo` struct.
2. How much state should live on the Definition vs the Instance (especially for simple one-shot resources).
3. Whether the Factory should be a dedicated `UHarvestableFactorySubsystem` or methods on a broader `UEnvironmentSubsystem` / `UResourceSubsystem`.
4. Branch / part damage: component-based, hit-zone based, or purely mesh-section based?
5. Falling trees: pure physics, animation + physics, or rooted physics constraint during the fall?
6. Save / load strategy for partially harvested resources and lazy Instances.
7. Whether very large “Items” that start as Harvestables (fallen trees) need special two-handed or “process in place” rules inside the Item system.
8. Crop-specific tuning (exact durations, multiplier curves, watering) once a test crop is in place.
